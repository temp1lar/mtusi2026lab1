## Запуск из чистой копии

Нужны Docker с Linux containers, Python 3.9+ и интернет для первой сборки.
Внешних NuGet-пакетов нет. SDK 10.0.403, runtime ASP.NET Core 10.0.14;
точные версии указаны в Dockerfile, SDK дополнительно в global.json.
Теги версий закреплены, digest не закреплён. Dev-зависимости исходного задания —
requirements-dev.txt; собственные Python-тесты дополнительных пакетов не требуют.

Одна команда из корня проекта: `python3 scripts/verify_docker.py`
(Windows: `python scripts/verify_docker.py` или `py -3 scripts/verify_docker.py`).
Она собирает образ, публикует случайный localhost-порт, ждёт healthy,
запускает тесты и жизненный цикл, сохраняет `evidence/docker-verification.txt`.

Ручной путь:

```sh
cp .env.example .env
docker build -t mtusi-messenger:lab1 .
docker run --name mtusi-messenger-lab1 -p 127.0.0.1:8080:8080 --env-file .env mtusi-messenger:lab1
# Во втором терминале, дождаться HTTP 200 /health/ready:
make test-all
docker stop --time 10 mtusi-messenger-lab1
docker start mtusi-messenger-lab1
```

На Windows вместо cp используйте Copy-Item; вместо make — команды из START_HERE.md.
Остановка безопасно завершает процесс, **но все учебные данные намеренно теряются**.
Удаление стенда: `docker rm -f mtusi-messenger-lab1`. Миграций, volumes и secrets в lab1 нет.
Исходный пример .env сохранён. APP_HOST определяет bind (default 0.0.0.0), APP_PORT —
порт (8080), APP_ENV — метку окружения в стартовом логе (lab), а не режим ASP.NET Development.
`.env` читает docker --env-file; приложение читает уже переданные переменные окружения.

## Архитектура и решения

Один процесс Kestrel, одно singleton in-memory хранилище. Источник истины — память
Dictionary/HashSet/List. API, идентификация и хранение разделены интерфейсами;
операции хранилища имеют асинхронные сигнатуры для будущего SQL I/O.

Одна блокировка защищает чтения/записи и составные действия. Chat содержит read-only
копию участников, страницы — отдельные снимки коллекций. Уникальность username,
создание чата и добавление сообщения атомарны относительно других операций этого процесса.
Чужой чат скрыт за 404; сервер извлекает sender_id из действительного X-User-Id.

Сортировка `(created_at,id)`, keyset cursor с HMAC и привязкой к запросу. Строго
возрастающие timestamp под lock не позволяют новым вставкам оказаться раньше cursor
при откате часов. Это не межзапросная snapshot-изоляция и не распределённые часы.
Внешних критических зависимостей readiness нет. При остановке новые запросы отклоняются;
HostOptions.ShutdownTimeout=5s. Health probe — встроенный HttpClient, без curl в образе.

## Эксперименты и отказы

Это проверка корректности для оценки 4, **не нагрузочное исследование на 5**.
Профиль: 10 потоков/клиентов, барьер старта, 10 последовательных отправок каждым,
новый отдельный чат, затем чтение всех страниц по 13 записей и сравнение объектов.
Последний успешный запуск: 100 записей, 100 уникальных ID, общее время сценария 0.106s.
Тест содержит и чтение/проверку, поэтому это число не выдаётся за write throughput.
Прогрев, p95/p99, RSS/CPU и предел масштабирования не исследовались, выводов о них нет.
Сведения о локальной среде: evidence/environment.txt. Docker runner задаёт 2 CPU / 512 MiB;
эти лимиты ещё не были применены к реально запущенному контейнеру.

## Ограничения и следующие шаги

Нельзя масштабировать на две реплики с раздельной памятью. Нет сохранности при crash/restart,
надёжной аутентификации, квот и ограничения общего числа сообщений. Общий lock и сортировка
истории ограничивают масштаб; неограниченный рост состояния способен исчерпать память.
JSON body ограничен 1 MiB, текст — контрактными 4000 code points.
